Hello everyone. I'm Geliang from the MPTCP community. I've been one of the
core upstream developers of MPTCP since 2020. I live in Beijing, China,
and work at a Chinese Linux distribution company called Kylin Software.

Here I bring a proposal to add TLS support for MPTCP.

MPTCP did not support TLS before. The two protocols conflict with each other
to some extent because both MPTCP and TLS use the ULP (Upper Layer Protocol).
ULP settings, including TLS configurations, are disabled in MPTCP.

This proposal presents a solution to make MPTCP and TLS compatible,
and to make MPTCP and TLS work together.

Introduction to MPTCP

What is MPTCP

- Multipath TCP or MPTCP is an extension to the standard TCP and is
  described in RFC 8684.
- MPTCP is implemented via TCP Options, kind number of MPTCP is 30.
- It allows a device to make use of multiple interfaces at once to send
  and receive TCP packets over a single MPTCP connection.
- MPTCP can aggregate the bandwidth of multiple interfaces or prefer the
  one with the lowest latency. It also allows a fail-over if one path is
  down, and the traffic is seamlessly reinjected on other paths.
- Introduced in Linux kernel v5.6

For more details, please visit the project website: https://www.mptcp.dev

]

Here I will give a very brief introduction to MPTCP.

MPTCP, or Multipath TCP, is an extension to the standard TCP and is
defined in RFC 8684. MPTCP is implemented via TCP options. A dedicated
TCP option is defined for MPTCP, and its kind number is 30. It allows a
device to use multiple network interfaces at the same time to send and
receive TCP packets /ˈpæk.ɪt/ over a single connection.

MPTCP can be used to combine the bandwidth of multiple interfaces or to
choose the best path with the lowest latency. It also supports
fail-over /ˈfeɪl/: if one path goes down, traffic is smoothly switched to
another path without interruption.

It was introduced in Linux kernel 5.6. After more than six years of
development, it has become mature /məˈtʃʊə/ and stable, and more and more
network applications already support MPTCP.

For more details, please visit the project website: mptcp.dev

How to use MPTCP?

- Address config: ip mptcp (manual), mptcpd daemon or Network Manager (automatic)

	# ip mptcp endpoint add 10.1.2.2 subflow

- Create MPTCP socket:

	fd = socket(AF_INET, SOCK_STREAM, IPPROTO_MPTCP);

  or force with 'mptcpize' or 'mptcpify-bpfcc' (no code change)

- Use: same as TCP sockets

  kernel creates multiple TCP subflows to send and receive data

]

How to use MPTCP?

First, we need to do address /əˈdres/ configuration to let MPTCP know
which IP addresses are available. This is handled by the path manager.
We can use 'ip mptcp' commands to do it manually, or we can use the
MPTCP daemon (ˈdiː.mən) (mptcpd) or Network Manager to do it automatically.

Then, we need to create MPTCP sockets instead of TCP ones on both the
server side and the client side. If only one side uses MPTCP, the connection
will fall back /fɔːl bæk/ to TCP. We need to explicitly pass the protocol
number IPPROTO_MPTCP (that is 262, not IPPROTO_TCP) as the third parameter of the socket()
syscall to create an MPTCP socket. Alternatively, without changing any code,
we can use 'mptcpize' or the BPF tool to force a TCP application to use MPTCP.

After the MPTCP sockets are created, we can use them just like TCP sockets,
with no difference. Inside the MPTCP protocol stack /stæk/, multiple TCP
sockets are created in kernel space to send and receive data, based on the
address configuration; we call each of these TCP sockets a subflow.

                },
        };
	setsockopt(fd, SOL_TLS, TLS_RX, (void *)&tls_rx, sizeof(tls_rx));

get:
	getsockopt(fd, IPPROTO_TCP, TCP_ULP, buf, &buflen);		("mptcp")

Problem:

	- TLS is configured through ULP
	- MPTCP also uses ULP for subflow management
	- Every subflow's ULP is occupied by MPTCP ("mptcp")
	- getsockopt(ULP) returns the first subflow's ULP
	- Setting TLS on MPTCP returns NOT SUPPORTED

]

How to configure TLS?

TLS is configured /kənˈfɪɡəd/ through the ULP socket option. Here is the typical code.

First, we use setsockopt to set the ULP name to "tls". Then we need to configure the
TLS version and cipher type for both the transmit side and the receive side.

But if we set TLS for an MPTCP socket, we will get an error code of 'NOT SUPPORTED',
because MPTCP also uses ULP for subflow management.

The ULP of every subflow is occupied by MPTCP, so every subflow's ULP name is "mptcp".
We can verify this by doing getsockopt(ULP) on an MPTCP socket, it returns the ULP
name of the first subflow, which is "mptcp".

So we cannot use TLS for MPTCP sockets. That is the problem.

Why do we need MPTCP TLS?

Some MPTCP-adapted applications need to use TLS for encryption.

The first one is lighttpd, a secure web server that already supports MPTCP. In
2024, lighttpd developers reported that one feature of lighttpd did not work with
MPTCP because TLS was not supported. We opened an issue on GitHub to address it,
and this issue was assigned to me. I tried to add MPTCP TLS support for the first
time, but found it very difficult. It is not simply a matter of adding a missing
socket option. So this feature was put on hold.

The second one is NVMe over MPTCP. One year later, while adding MPTCP support for
NVMe, I encountered the TLS requirement again. With MPTCP, NVMe can aggregate the
bandwidth of all available network devices, achieving a multi-fold performance
improvement than TCP in multiple /ˈmʌl.tɪ.pl/ network devices environments. But
NVMe over TCP needs to use TLS for encryption. If MPTCP support is added, MPTCP
also needs to provide the same TLS support. To avoid blocking the NVMe over MPTCP
feature, it was time to implement MPTCP TLS.

These are the main motivations behind this work.

Key points:

	- Every subflow's ULP is occupied by MPTCP

The first priority on the MPTCP side is to enable TLS configuration on MPTCP.

The ULP of every subflow is occupied by MPTCP, but the ULP of the MPTCP socket
itself is unused. So the only place where TLS can be set is the ULP of the
MPTCP socket.

So in setsockopt, we check whether the ULP is "tls", and if so, we set it on
the "sk", which is the MPTCP socket.

In getsockopt, we read the ULP of the MPTCP socket, rather than reading
the ULP of the first subflow as before.

This is the implementation for the MPTCP socket option.

Next, implement MPTCP-specific functions for TLS usage

The current TLS implementation is bound to TCP, and it calls nine TCP functions
on the TCP socket to send and receive TCP data. But with MPTCP, we need to deal
with the MPTCP socket, which in turn manages the different subflows. So we cannot
simply call the hardcoded TCP functions; we need MPTCP-specific versions of them.

Fortunately, over half of these MPTCP-specific functions are already implemented
in MPTCP, and only four of them need to be implemented from scratch: they are
mptcp_read_sock, mptcp_read_done, mptcp_inq and mptcp_rate_check_app_limited.

After all these functions are implemented on the MPTCP side, we are ready to add
MPTCP support on the TLS side.

TLS Implementation in RFC version

TCP is currently hardcoded in a few places, and all these places should
switch between different functions for TCP and MPTCP

A struct tls_prot_ops is defined to describe the differences between TCP and MPTCP:

struct tls_prot_ops {
	int (*sendmsg_locked)(...);
	int (*inq)(...);
	int (*read_sock)(...);
	__poll_t (*poll)(...);

	void (*read_done)(...);
	struct sk_buff *(*recv_skb)(...);
	bool (*epollin_ready)(...);

	void (*check_app_limited)(...);
	bool (*lock_is_held)(...);
	int (*skb_get_header)(...);
	u32 (*get_skb_seq)(...);
};

struct tls_context {
	...
	const struct tls_prot_ops *ops;
	...
};

- Two instances: one for TCP, one for MPTCP
- Pointer set at TLS setup time
- Replaces hardcoded TCP calls
- Works, but too much protocol awareness
- This struct is deprecated in later versions.

]

The implementation on the TLS side went through two different versions.
In the RFC version, I defined a new structure tls_prot_ops, and the implementation
was built around this structure. In later versions, however, this structure
was deprecated /ˈdep.rə.keɪ.tɪd/, and a new approach that fits the TLS framework
better was used. Here I will introduce both versions in turn.

On this slide, this is the RFC version of the implementation.
Here I defined a struct tls_prot_ops to put all the functions called by TLS
into it to describe the differences between TCP and MPTCP for TLS usage.

I defined two instances of this structure, one for TCP and the other for MPTCP.

I added a pointer to this structure in tls_context. When TLS is set, this
pointer is initialized to a different instance based on whether the socket
protocol is TCP or MPTCP.

Afterwards, we access the instance through the pointer in tls_context, and
call the corresponding interfaces of this instance to replace the originally
hardcoded TCP functions.

This RFC version works, but there is still a lot of room for improvement.
We should minimize TLS's awareness of TCP or MPTCP protocols.

In later versions, I refactored this part of the code, and eventually removed this
structure entirely.

The first refactoring is we dropped the first four interfaces of this structure.

The first four interfaces in struct tls_prot_ops are generic socket operations
that are already defined in struct proto_ops. There is no need to redefine them
in struct tls_prot_ops; we can access them directly through struct proto_ops.

However, two interfaces, read_sock and poll, are overwritten by TLS. If we
want to access the interfaces of the original protocol, we need to save struct
proto_ops before they are overwritten. Just like the socket proto pointer in
struct tls_context is used to save the original struct proto, we added the
socket proto_ops pointer in it to save the original struct proto_ops.

In this way, in TLS we can access the interfaces of the original protocol through
the saved socket proto_ops pointer, replacing the calls of TCP functions.

The second refactoring is the last four interfaces in struct tls_prot_ops can
also be dropped.

1 check_app_limited

When running MPTCP TLS, the code crashed in tls_push_sg. Debugging showed
that the crash occurred when an MPTCP socket was passed to the TCP version
of check_app_limited. We needed to implement an MPTCP-specific version of
check_app_limited for MPTCP sockets, so a check_app_limited interface was
added here.

Recently I found that this check_app_limited call in tls_push_sg is
duplicate, since it is always called inside sendmsg_locked. And
sendmsg_locked in called in tls_push_sg too. So I removed this
check_app_limited call, and this interface is no longer needed.

2 lock_is_held

Then we encountered a deadlock problem when running MPTCP TLS.
TLS needs to call read_sock from softirq context, and mptcp_read_sock
holds an additional MPTCP data lock. So we added a lock_is_held
interface to customize MPTCP's behavior to check whether the MPTCP data
lock is held.

Recently, Paolo's patch removed the MPTCP data lock in mptcp_read_sock,
so this interface is no longer needed either.

3 skb_get_header

Next, during testing we found that TLS decryption sometimes failed on MPTCP.
Debugging showed that this happened in the overlapping skbs scenario /sɪˈnɑː.ri.əʊ/.
MPTCP is more likely to trigger overlapping skbs than TCP, and in that case
the TLS header cannot be read correctly, so decryption fails. We added a
skb_get_header interface to customize MPTCP's behavior to read the TLS header
correctly from MPTCP sk_buff.

Recently this overlapping skbs issue was fixed upstream in TLS, so this
interface is no longer needed either.

4 get_skb_seq

The last one is get_skb_seq. Because the sk_buff control block layouts of TCP
and MPTCP are different, we needed to use this interface to obtain the seq from the
sk_buff control block separately.

Now Paolo's patch has made the MPTCP sk_buff control block layout compatible with
TCP, so this interface is no longer needed either.

Limitation

- TLS is not supported by fallback MPTCP sockets
  will be supported in the future

- Hardware TLS offload is not supported
  per-subflow hardware offload is very difficult on MPTCP
  possible approach: trigger MPTCP fallback, then use the first subflow's hardware TLS offload

]

MPTCP TLS support currently has two key limitations.

First, only non-fallback MPTCP sockets support TLS.
TLS support for fallback mode is still under development.

Second, only software TLS encryption is supported for MPTCP;
hardware TLS is not supported.

Hardware TLS offload typically requires binding to a specific network
device. Per-subflow hardware TLS offload is very difficult to implement
on MPTCP: the NIC would need to see the whole traffic, identify subflows
that belong to the same connection, and deal with the MPTCP data sequence
numbers. That is already much more complex than just dealing with one
flow and keeping an offset.

The only possible approach is to trigger MPTCP fallback when hardware TLS
is setting, and then use the hardware TLS offload only on the first subflow.

on the target side.

reads and writes on this device, and no errors occur, which shows that it works
