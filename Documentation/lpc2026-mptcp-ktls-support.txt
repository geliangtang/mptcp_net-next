MPTCP has historically lacked TLS support due to fundamental conflicts
in how both protocols manage the Upper Layer Protocol (ULP) stack within
the Linux kernel.

This proposal presents a solution to make MPTCP and Kernel TLS (KTLS) compatible.
And make MPTCP and TLS can work together.

Introduction to MPTCP

- Multipath TCP or MPTCP is an extension to the standard TCP and is
  described in RFC 8684.
- MPTCP is implemented via TCP Options, kind number of MPTCP is 30.
- It allows a device to make use of multiple interfaces at once to send
  and receive TCP packets over a single MPTCP connection.
- MPTCP can aggregate the bandwidth of multiple interfaces or prefer the
  one with the lowest latency. It also allows a fail-over if one path is
  down, and the traffic is seamlessly reinjected on other paths.
- Introduced in Linux kernel v5.6

For more details, please visit the project website: https://www.mptcp.dev

]

Here I will give a very brief introduction to MPTCP.

MPTCP, or Multipath TCP, is an extension to the standard TCP and is
defined in RFC 8684. MPTCP is implemented via TCP options. A dedicated
TCP option is defined for MPTCP, and its kind number is 30. It allows a
device to use multiple network interfaces at the same time to send and
receive TCP packets /ˈpæk.ɪt/ over a single connection.

MPTCP can be used for combining the bandwidth of multiple interfaces or
choosing the best path with the lowest latency. It also supports
fail-over /ˈfeɪl/: if one path goes down, traffic is smoothly switched to another
path without interruption.

It was introduced in Linux kernel 5.6. After more than six years of
development, it has become mature /məˈtʃʊə/ and stable, and more and more
network applications already support MPTCP.

For more details, please visit the project website: mptcp.dev

Introduction to MPTCP

How to use MPTCP?

- Address config: ip mptcp (manual) or mptcpd daemon (automatic)

- Create socket:

	fd = socket(AF_INET, SOCK_STREAM, IPPROTO_MPTCP);

  or force with BPF (no code change)

- Use: same as TCP sockets; kernel creates multiple TCP subflows to send and receive data

-
	err = getsockopt(fd, IPPROTO_TCP, TCP_ULP, buf, &buflen);

	err = setsockopt(fd, IPPROTO_TCP, TCP_ULP, "tls", sizeof("tls"));
	err = setsockopt(fd, SOL_TLS, TLS_TX, (void *)&tls_tx, sizeof(tls_tx));
	err = setsockopt(fd, SOL_TLS, TLS_RX, (void *)&tls_rx, sizeof(tls_rx));

]

How to use MPTCP?

First, we need to do address /əˈdres/ configuration, which is handled by
the path manager. We can use 'ip mptcp' commands to do it manually,
or we can use the MPTCP daemon (ˈdiː.mən) (mptcpd) to do it automatically.

Then, we need to create MPTCP sockets both on the server side and client side.
If only one side uses MPTCP, the connection will fall back /fɔːl bæk/ to TCP.
We need to explicitly pass the protocol number IPPROTO_MPTCP (that is 262)
as the third parameter of socket() syscall to create an MPTCP socket.
Or, without changing any code, we can use the BPF tool to force a TCP
application to use MPTCP.

After the MPTCP sockets are created, we can use them just like TCP sockets,
with no difference. Inside the MPTCP protocol stack /stæk/, multiple TCP
sockets are created in kernel space to send and receive data, based on the
address configuration; we call each TCP socket a subflow.

当然我们也可以像设置TCP sockopt那样去设置MPTCP sockopt，但是我们不能set TLS.
If you set TLS for an MPTCP socket, you will get an error code of 'NOT SUPPORTED'.
我们可以看到，tls是通过 TCP_ULP来设置的，但是坏消息是MPTCP也ULP来实现subflow管理。

+static int subflow_ulp_init(struct sock *sk)
+{
+	struct mptcp_subflow_context *ctx;
+	struct tcp_sock *tp = tcp_sk(sk);
+	int err = 0;
+
+	/* disallow attaching ULP to a socket unless it has been
+	 * created with sock_create_kern()
+	 */
+	if (!sk->sk_kern_sock) {
+		err = -EOPNOTSUPP;
+		goto out;
+	}
+
+	ctx = subflow_create_ctx(sk, GFP_KERNEL);
+	if (!ctx) {
+		err = -ENOMEM;
+		goto out;
+	}
+
+	pr_debug("subflow=%p, family=%d", ctx, sk->sk_family);
+
+	tp->is_mptcp = 1;
+out:
+	return err;
+}
+
+static void subflow_ulp_release(struct sock *sk)
+{
+	struct mptcp_subflow_context *ctx = mptcp_subflow_ctx(sk);
+
+	if (!ctx)
+		return;
+
+	kfree_rcu(ctx, rcu);
+}

+	.name		= "mptcp",
+	.owner		= THIS_MODULE,

+	.release	= subflow_ulp_release,
+};

+void mptcp_subflow_init(void)
+{

+		panic("MPTCP: failed to register subflows to ULP\n");

Why do we need MPTCP TLS?

Enabling TLS on MPTCP is a highly demanded /dɪˈmɑːnd/ feature.

Several use cases have expressed strong demand for TLS functionality after adopting MPTCP,
including: lighttpd, a secure web server that already supports MPTCP and
requires TLS for encrypted communications; and NVMe over MPTCP, where
NVMe over TCP benefits from MPTCP's multipath capabilities but requires
TLS for data confidentiality and integrity.

Beyond these specific use cases, the current TLS implementation in the Linux kernel is tightly
coupled with TCP. By extending MPTCP to support TLS, we make the TLS
code structure more flexible and extensible. This work also serves as a
practical validation of the TCP ULP framework, providing a real-world
example of two ULP features operating in conjunction.

These are the main motivations behind this work.

I finally found a solution to make MPTCP and TLS compatible, and
implemented MPTCP support on the TLS side and enabled TLS settings on
the MPTCP side. Need to say, only software TLS encryption is supported
for MPTCP right now; hardware TLS has not yet been developed.

I started working on this feature about a year ago. Currently, the
implementation and testing are mostly done. Some code is upstreamed,
while most remains under review on MPTCP side, in RFC stage.

The modifications in the NVMe subsystem are minimal. Most of the code
changes are on the MPTCP side.

Here are the patchsets:

1 mptcp: implement .read_sock (/riːd/ underscore)

TLS uses read_sock interface for receiving data. However, it was
not implemented in MPTCP before /bɪˈfɔː(r)/, since all current use cases for MPTCP
are in userspace, where read_sock is not used. So my first task was to
implement this interface for MPTCP.

After several rounds of iteration, this set was merged into Linux kernel
in February this year. With this interface, we can add MPTCP support
/səˈpɔːt/ for NVMe now.

2 mptcp: reduce the differences between TCP and MPTCP for TLS usage

This is a series developed together with Paolo to reduce the differences
between TCP and MPTCP in the TLS code path. It includes removing the
offset in mptcp_skb_cb, syncing the MPTCP skb cb layout with the TCP one,
and deferring read_sock cleanup to mptcp_worker.

3 MPTCP KTLS support

This set is currently under review on MPTCP side, and I believe it will
be upstreamed this year.

4 selftests: tls: add mptcp test cases

5 mptcp: address stall under memory pressure

6 Enable KTLS for NVMe over MPTCP

This set adds basic MPTCP support for NVMe, but without TLS encryption /ɪnˈkrɪp.ʃən/.
It defines a new transport /ˈtræn.spɔːt/ type for MPTCP, which creates /kriˈeɪt/ MPTCP sockets
between the target (ˈtɑːɡɪt) and the host instead of TCP sockets.

Once TLS is supported /səˈpɔː.tɪd/ for MPTCP, using TLS for NVMe MPTCP becomes
straightforward /ˌstreɪtˈfɔː.wəd/. Only need to enable TLS setting in configfs
for the MPTCP transport type.

7 The next is about user space changes

User space tool, ktls-utils, is needed by NVME over MPTCP selftests, also need to add MPTCP support.

That's all the patch list.

The implementation on the MPTCP side is simple.

Inside the MPTCP protocol stack, one MPTCP socket manages multiple
subflows, and each subflow is a TCP socket. The MPTCP-side implementation
applies TLS settings to the MPTCP socket (msk) and does not synchronize
them down to the subflow sockets.

Limitation

]

MPTCP KTLS support currently has one key limitation.

MPTCP KTLS currently supports only software TLS encryption;
hardware TLS offload is not supported. The MPTCP socket is an abstract
transport-layer construct that does not correspond to a specific IP
address or network interface; it may span multiple interfaces with
differing hardware capabilities. This abstract nature is fundamentally
at odds with hardware TLS offload, which typically requires binding to
a specific network device. Hardware TLS support for MPTCP is therefore
not provided in this implementation.
