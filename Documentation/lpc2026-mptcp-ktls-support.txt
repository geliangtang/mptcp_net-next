Hello everyone. I'm Geliang from the MPTCP community. I've been one of the
core upstream developers of MPTCP since 2020. I live in Beijing, China,
and work at a Chinese Linux distribution company called Kylin Software.

Here I bring a proposal to add MPTCP support for TLS.

MPTCP did not support TLS before. They conflict with each other to
some extent because both MPTCP and TLS use the ULP (Upper Layer Protocol).
ULP settings, including TLS configurations, are disabled in MPTCP.

This proposal presents a solution to make MPTCP and TLS compatible,
and make MPTCP and TLS work together.

Introduction to MPTCP

What is MPTCP

- Multipath TCP or MPTCP is an extension to the standard TCP and is
  described in RFC 8684.
- MPTCP is implemented via TCP Options, kind number of MPTCP is 30.
- It allows a device to make use of multiple interfaces at once to send
  and receive TCP packets over a single MPTCP connection.
- MPTCP can aggregate the bandwidth of multiple interfaces or prefer the
  one with the lowest latency. It also allows a fail-over if one path is
  down, and the traffic is seamlessly reinjected on other paths.
- Introduced in Linux kernel v5.6

For more details, please visit the project website: https://www.mptcp.dev

]

Here I will give a very brief introduction to MPTCP.

MPTCP, or Multipath TCP, is an extension to the standard TCP and is
defined in RFC 8684. MPTCP is implemented via TCP options. A dedicated
TCP option is defined for MPTCP, and its kind number is 30. It allows a
device to use multiple network interfaces at the same time to send and
receive TCP packets /ˈpæk.ɪt/ over a single connection.

MPTCP can be used for combining the bandwidth of multiple interfaces or
choosing the best path with the lowest latency. It also supports
fail-over /ˈfeɪl/: if one path goes down, traffic is smoothly switched to another
path without interruption.

It was introduced in Linux kernel 5.6. After more than six years of
development, it has become mature /məˈtʃʊə/ and stable, and more and more
network applications already support MPTCP.

For more details, please visit the project website: mptcp.dev

Introduction to MPTCP

How to use MPTCP?

- Address config: ip mptcp (manual) or mptcpd daemon (automatic)

	# ip mptcp endpoint add 10.1.2.1 signal

- Create socket:

	fd = socket(AF_INET, SOCK_STREAM, IPPROTO_MPTCP);

  or force with BPF (no code change)

- Use: same as TCP sockets; kernel creates multiple TCP subflows to send and receive data

]

How to use MPTCP?

First, we need to do address /əˈdres/ configuration, which is handled by
the path manager. We can use 'ip mptcp' commands to do it manually,
or we can use the MPTCP daemon (ˈdiː.mən) (mptcpd) to do it automatically.

Then, we need to create MPTCP sockets instead of TCP ones both on the server side and client side.
If only one side uses MPTCP, the connection will fall back /fɔːl bæk/ to TCP.
We need to explicitly pass the protocol number IPPROTO_MPTCP (that is 262)
as the third parameter of socket() syscall to create an MPTCP socket.
Or, without changing any code, we can use the BPF tool to force a TCP
application to use MPTCP.

After the MPTCP sockets are created, we can use them just like TCP sockets,
with no difference. Inside the MPTCP protocol stack /stæk/, multiple TCP
sockets are created in kernel space to send and receive data, based on the
address configuration; we call each TCP socket a subflow.

If you set TLS for an MPTCP socket, you will get an error code
of 'NOT SUPPORTED'. As we can see, TLS is configured through TCP_ULP, but the bad news
is that MPTCP also uses ULP for subflow management.

We can verify this by doing getsockopt(TCP_ULP) on an MPTCP socket; it returns "mptcp"
as the TCP_ULP name.

The two protocols conflicted because both MPTCP and TLS utilize the ULP (Upper
Layer Protocol) infrastructure in the Linux kernel.

ULP settings, including TLS configuration, were disabled for MPTCP sockets.
That's the problem.

Why do we need MPTCP TLS?

Some MPTCP-adapted applications need to use TLS for encryption.

The first is lighttpd, a secure web server that already supports MPTCP. In
2024, lighttpd developers reported that MPTCP did not work because TLS was
not supported. We opened issue #480 on GitHub to address it, and this issue
was assigned to me. Later I tried to add MPTCP TLS support for the first
time, but found it very difficult. It is not simply to add a missing sockopt.
So this feature was put on hold.

The second is NVMe over MPTCP. One year later, while developing another
new MPTCP feature - adding MPTCP support for NVMe - I encountered the
TLS requirement again. NVMe over TCP can use TLS encryption. If MPTCP
support is added, MPTCP also needs to provide the same TLS support. To
avoid blocking the NVMe over MPTCP feature, I made up my mind that it
was time to implement MPTCP TLS support.

These are the main motivations behind this work.

1 mptcp: implement .read_sock (/riːd/ underscore)

TLS uses the read_sock interface for receiving data. However, it was
not implemented in MPTCP before /bɪˈfɔː(r)/, since all current use cases for MPTCP
are in userspace, where read_sock is not used. So my first task was to
implement this interface for MPTCP.

After several rounds of iteration, this set was merged into the Linux kernel
in February this year.

2 mptcp: reduce the differences between TCP and MPTCP for TLS usage

This is a series developed together with Paolo to reduce the differences
between TCP and MPTCP in the TLS code path. It includes removing the
offset in the MPTCP sk_buff Control Block (mptcp_skb_cb), syncing the MPTCP
skb cb layout with the TCP one, and deferring read_sock cleanup to
mptcp_worker.

3 MPTCP KTLS support

I implemented MPTCP support on the TLS side and enabled TLS settings on
the MPTCP side. This set is currently under review on the MPTCP side,
and I believe it will be upstreamed this year.

The implementation on the MPTCP side is simple.

Inside the MPTCP protocol stack, one MPTCP socket manages multiple
subflows, and each subflow is a TCP socket. The MPTCP-side implementation
applies TLS settings to the MPTCP socket (msk) and does not synchronize
them down to the subflow sockets.

This is the only way to make MPTCP and TLS compatible.

Limitation

- TLS currently is not supported by fallback MPTCP sockets.

- Hardware TLS offload is not supported.

]

MPTCP KTLS support currently has two key limitations.

First, only non-fallback MPTCP sockets support KTLS. Attempting to set
TLS on a fallback MPTCP socket is not supported. A separate patchset to
add TLS for fallback MPTCP sockets will be developed later.

Second, only software TLS encryption is supported for MPTCP right now;
hardware TLS has not been developed. And we have no plans to support it
in the future.

The MPTCP socket is an abstract transport-layer construct that does not
correspond to a specific IP address or network interface; it may span
multiple interfaces with differing hardware capabilities. This abstract
nature is fundamentally at odds with hardware TLS offload, which typically
requires binding to a specific network device. Hardware TLS support for
MPTCP is therefore not provided in this implementation.
