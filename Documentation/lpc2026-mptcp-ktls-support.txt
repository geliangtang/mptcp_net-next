Here I bring a proposal to add TLS support for MPTCP.

MPTCP did not support TLS before. The two protocols conflict with each
other to some extent because both MPTCP and TLS use the TCP ULP (Upper
Layer Protocol). ULP settings, including TLS configurations, are disabled
in MPTCP.

make the two protocols work together.

Introduction to MPTCP
What is MPTCP

- Multipath TCP or MPTCP is an extension to the standard TCP and is
  described in RFC 8684.
- MPTCP is implemented via TCP Options, kind number of MPTCP is 30.
- It allows a device to make use of multiple interfaces at once to send
  and receive TCP packets over a single MPTCP connection.
- MPTCP can aggregate the bandwidth of multiple interfaces or prefer the
  one with the lowest latency. It also allows a fail-over if one path is
  down, and the traffic is seamlessly reinjected on other paths.
- Introduced in Linux kernel v5.6

For more details, please visit the project website: https://www.mptcp.dev

]

Here I will give a very brief introduction to MPTCP.

MPTCP, or Multipath TCP, is an extension to the standard TCP and is
defined in RFC 8684. MPTCP is implemented via TCP options. A dedicated TCP
option is defined for MPTCP, and its kind number is 30. It allows a device
to use multiple /ˈmʌl.tɪ.pl/ network interfaces at the same time to send
and receive TCP packets /ˈpæk.ɪt/ over a single connection.

MPTCP can be used to combine the bandwidth of multiple network interfaces
or to choose the best path with the lowest latency. It also supports
fail-over /ˈfeɪl/: if one path goes down, traffic is smoothly switched to
another path without interruption.

It was introduced in Linux kernel 5.6. After more than six years of
development, it has become mature /məˈtʃʊə/ and stable, and more and more
network applications already support MPTCP.

For more details, please visit the project website: mptcp.dev

Introduction to MPTCP
How to Use MPTCP?

- Address config: ip mptcp (manual), mptcpd or Network Manager (automatic)

	# ip mptcp endpoint add 10.1.2.2 subflow

- Create MPTCP socket:

	fd = socket(AF_INET, SOCK_STREAM, IPPROTO_MPTCP);

  or force with 'mptcpize' or 'mptcpify-bpfcc' (no code change)

- Use: same as TCP sockets

  kernel creates multiple TCP subflows to send and receive data

]

How to use MPTCP?

First, we need to do address /əˈdres/ configuration to let MPTCP know
which IP addresses are available. This is handled by the MPTCP path
manager. We can use 'ip mptcp' commands to do it manually, or we can use
either the MPTCP daemon (ˈdiː.mən) or Network Manager to do it
automatically.

Then, we need to create MPTCP sockets instead of TCP ones on both the
server side and the client side. If only /ˈəʊn.li/ one side uses MPTCP,
the connection will fall back /fɔːl bæk/ to TCP. We need to explicitly
pass the protocol number IPPROTO_MPTCP (that is 262, not IPPROTO_TCP)
as the third parameter of the socket() syscall to create an MPTCP socket.
Alternatively, without changing any code, we can use 'mptcpize' or the
BPF tool to force a TCP application to use MPTCP.

After the MPTCP sockets are created, we can use them just like TCP
sockets, with no difference. Inside the MPTCP protocol stack /stæk/,
multiple TCP sockets are created in kernel space to send and receive data,
based on the address configuration; we call each of these TCP sockets a
subflow.

How to configure TLS?

TLS is configured /kənˈfɪɡəd/ through the ULP socket option. Here is the
typical code.

First, we use setsockopt (set-sock-opt /ɒpt/) to set the ULP name as "tls".
Then we use setsockopt to configure the TLS version and cipher type for both
the transmit side and the receive side.

But if we set TLS for an MPTCP socket, we will get an error code of 'NOT
SUPPORTED', because MPTCP also uses ULP for subflow management.

The ULP of every subflow is occupied by MPTCP, so its ULP name is "mptcp".
We can verify this with getsockopt of ULP on an MPTCP socket: it returns
the first subflow's ULP name, that is "mptcp".

So we cannot use TLS for MPTCP sockets. That is the problem.

Why do we need MPTCP TLS?

Some MPTCP-adapted applications need to use TLS for encryption.

The first one is lighty, a secure web server that already supports MPTCP.
In 2024, lighty developers reported to us that one feature of lighty did
not work with MPTCP because TLS was not supported. We opened an issue on
GitHub to address it, and this issue was assigned to me. I tried to add
MPTCP TLS support for the first time, but found it very difficult. It is
not simply a matter of adding a missing socket option; much more work is
needed. So this feature was put on hold.

The second one is NVMe over MPTCP. One year later, while adding MPTCP
support for NVMe, I encountered the TLS requirement again. With MPTCP,
NVMe can aggregate the bandwidth of all available network devices,
achieving a multi-fold performance improvement over TCP in multiple
network device environments. But NVMe over TCP needs to use TLS for
encryption. If MPTCP support is added, MPTCP also needs to provide the
same TLS support. To avoid blocking the NVMe over MPTCP feature, it was
time to implement MPTCP TLS.

These are the main motivations behind this work.

The next is implementation.

The first step on the MPTCP side is to enable TLS configuration.

As mentioned, the ULP of every subflow is occupied by MPTCP, but the ULP
of the MPTCP socket itself is unused. So the only place where TLS can be
set is the ULP of the MPTCP socket.

With this, in setting socket option, we check whether the ULP is "tls",
and if so, we set it on the "sk", which is the MPTCP socket.

In getting socket option, we read the ULP name of the MPTCP socket, not
the ULP name of the first subflow as before.

This is the implementation for the MPTCP socket option.

 - TCP_SKB_CB			->	MPTCP_SKB_CB

Next, implement MPTCP-specific helpers for TLS usage.

As mentioned, the current TLS implementation is bound to TCP, and it uses
nine TCP helpers on the TCP socket to send and receive data for TLS
encryption and decryption. But with MPTCP, TLS needs to deal with the MPTCP
socket, which in turn manages the different subflows, that are TCP sockets.
So we cannot simply use the hardcoded TCP helpers; we need MPTCP-specific
versions of them.

Fortunately, over half of these MPTCP-specific helpers are already
implemented in MPTCP, and only three of them need to be implemented from
scratch, based on the TCP implementations and adapted to the MPTCP behavior.

After all these helpers are implemented on the MPTCP side, we are ready to
add MPTCP support on the TLS side.

On the TLS side, the encryption and decryption themselves are the same for
TCP and MPTCP. The difference is how data is received and sent. So we need
to replace all the places that directly use these nine TCP helpers with
indirect calls that dispatch /dɪˈspætʃ/ based on the protocol: for a TCP
socket, call the TCP helper; for an MPTCP socket, call the MPTCP helper.
In this way, the same TLS code can work with both TCP and MPTCP, without
any hardcoded protocol calls.

There are many approaches to do this. For example, we could add nine wrappers
that switch based on the protocol, or define a new structure that holds
all nine helpers as ops /ɒps/. But here we did not handle all of them
in one uniform way. Instead, we grouped them: the first four are generic
socket ops, and the next three are receive-related ops. We use a different
approach for each group.

Let's go through the TLS-side implementation group by group.

Let's start with the generic socket ops.

The four helpers - tcp_sendmsg_locked, tcp_read_sock, tcp_poll and tcp_inq -
are generic /dʒəˈner.ɪk/ socket operations in struct proto_ops. They can
switch between protocols easily through indirect calls in proto_ops.

However, two of the ops in struct proto_ops, read_sock and poll,
are overwritten by TLS. To access the original ones, we need to save
proto_ops before they are overwritten. Just as we save the original struct
proto in tls_context, we also save the original proto_ops there.

In this way, TLS can reach the original ops through the saved proto_ops
in tls_context, replacing the direct TCP calls.

Next, receive-related ops.

We define a new structure to describe the differences between TCP and MPTCP for
the receive-related helpers.

This structure has a protocol field and three ops: recv_ready, recv_skb,
and read_done. We define two instances, one for TCP and the other for MPTCP.
The TCP instance keeps tcp_epollin_ready, tcp_recv_skb and tcp_read_done; the
MPTCP instance uses MPTCP-specific helpers.

We add a pointer to this structure in struct tls_sw_context rx. When TLS is set,
we look up the right instance based on the socket protocol, and set it to the
pointer.

In the receive path, instead of the hardcoded TCP calls, we call the
corresponding op through the pointer in the rx context.

The Final Two

 - check_app_limited

	mptcp: track app-limited state in mptcp_sendmsg_locked
	tls: drop duplicate check_app_limited in tls_push_sg

 - TCP_SKB_CB

	mptcp: sync mptcp skb cb layout with tcp one	(Paolo Abeni)
	tls: read skb sequence through a TLS_SKB_CB overlay

Now only two helpers are left that need to switch between TCP and MPTCP.
We handled them in two opposite ways: one was removed, and the other was
added.

1 check_app_limited

The MPTCP-specific check_app_limited is called inside mptcp_sendmsg_locked,
mirroring what tcp_sendmsg_locked does. So check_app_limited is always
called through sendmsg_locked, whether on TCP or MPTCP.

This means the direct check_app_limited call in tls_push_sg is duplicate,
and can be removed, because sendmsg_locked is also called there.

In this way, check_app_limited is covered by the existing protocol switch
inside sendmsg_locked.

2 TCP_SKB_CB

The last one is the TCP SKB CB macro. MPTCP uses another one, MPTCP SKB CB,
to obtain the MPTCP sk_buff control block.

Now Paolo's patch has made the MPTCP sk_buff control block layout compatible
with TCP, so we can define a new unified TLS_SKB_CB macro to obtain the
sk_buff control block for TLS, without caring whether it is TCP or MPTCP.
We use it to replace all the TCP_SKB_CB calls in TLS code.

At this point, we have replaced all the direct TCP calls. That's the entire
implementation on the TLS side.

Bugfixes

 - A deadlock in mptcp_read_sock

	mptcp: defer read_sock cleanup to mptcp_worker	(Paolo Abeni)

 - TLS decryption failed on overlapping skbs

	tls: fix RX desync on overlapping skbs	(Maximilian Immanuel Brandtner)

 - TLS operation cache shared by TCP and MPTCP caused a crash

	tls: add protocol dimension to tls operation cache

]

After the implementation, we started testing and found many bugs.
Here are three typical ones:

1 A deadlock in mptcp_read_sock

We hit a deadlock during testing. TLS needs to call read_sock from
bottom-half context sometimes, but the cleanup part of mptcp_read_sock
holds the MPTCP data lock. This causes a deadlock.

The fix was Paolo's patch, which defers the cleanup part of mptcp_read_sock
to the mptcp worker. In this way, mptcp_read_sock can also be called from
bottom-half context, and no deadlock occurs.

2 TLS Decryption failed on overlapping skbs

Next, TLS decryption sometimes failed on MPTCP. Debugging showed that it
happened in the overlapping skbs situation. MPTCP is more likely to trigger
overlapping skbs than TCP, and in that case the TLS header cannot be read
correctly, so decryption fails. We tried several approaches to handle
overlapping skbs specially on the MPTCP side, to make sure TLS can find
the header correctly.

Fortunately, this overlapping skbs issue was fixed upstream in TLS
recently, so no need to handle it on the MPTCP side anymore.

3 TLS operation cache shared by TCP and MPTCP caused a crash

The TLS operation cache is used to store the protocol operations that
TLS needs, so that TLS can call them efficiently /ɪˈfɪʃ.ənt.li/ without
rebuilding them every time.

When only TCP was supported, there were just two variants to cache:
IPv4 and IPv6. So the cache used to be indexed only by IP version.

But once MPTCP was added, TCP and MPTCP sockets in the same IP version
ended up using the same cache entries, which caused type confusion and
a crash.

To fix this, we gave the cache a protocol dimension /daɪˈmen.ʃən/, so
that TCP and MPTCP have their own entries.

In this way, TCP and MPTCP no longer share the same cache, so MPTCP TLS
no longer affects existing TCP TLS sockets.

Limitations

 - TLS is not supported by fallback MPTCP sockets

	Will be supported in the future

 - Hardware TLS offload is not supported

	Per-subflow hardware offload is very difficult to implement on MPTCP
	Possible approach: trigger MPTCP fallback

]

MPTCP TLS support currently has two key limitations.

First, only non-fallback MPTCP sockets support TLS. TLS support for MPTCP
in fallback mode is still under development.

Second, only software TLS encryption is supported for MPTCP; hardware TLS
is not supported.

Hardware TLS offload typically requires binding to a specific network
device, but MPTCP sends and receives data over every network device. This
makes per-subflow hardware TLS offload very difficult to implement on
MPTCP.

The only possible approach is to trigger MPTCP fallback when hardware TLS
is set, and then only use the hardware TLS offload on the network device
of the first subflow.

Here we use a real-world case to verify the correctness of MPTCP TLS:
using TLS for NVMe over MPTCP.

As we can see, when we run "nvme discover" with TLS, the output shows
that the transport type is "mptcp" and the security type is "tls13",
which indicates that MPTCP TLS is working properly.

Then when we run "nvme connect" with TLS, a new NVMe controller with TLS
is created on the target side.

When we run "nvme list", a new NVMe device appears. We can use "fio" to
benchmark reads and writes on this device, and no errors occur, which
shows that it works well.
